# Architecture Map

A guide to the Body Reconstruction repository. The app is React + TypeScript built with Vite. With Supabase configured, signed-in users store data in PostgreSQL; the previous IndexedDB database remains available for local migration and development without cloud configuration.

Before changing code, follow `AGENTS.md` and inspect relevant guides in `skills/*/SKILL.md` when the local `skills/` directory is available. `skills/CODE_PRACTICES.md` contains the general repository coding practices.

The detailed React refactor and desktop/mobile design plan is in `REACT_REFACTOR_DESIGN_PLAN.md`. Consult it before structural UI work; it is a plan, not a description of implemented behavior.

## Modules and Responsibilities

- **`src/main.tsx` — application composition.** Initializes React, selects the persistence adapter, connects profile data and action hooks to the shell and views, and handles the historical workout editor. Start here when changing navigation between screens or wiring a view to persistence.
- **Navigation:** `src/app/navigation.ts` defines typed view names and GitHub Pages-safe `?view=` URLs. `src/app/useNavigation.ts` owns tab state, browser Back handling, and an asynchronous leave guard using the in-app confirmation dialog. `main.tsx` also registers `beforeunload` protection for unsaved forms and allows an already-confirmed app update to reload once. The editor route requires an in-memory draft; a direct editor link resolves to History.
- **Responsive app shell:** `src/app/AppShell.tsx` owns the sidebar, header, account/profile controls, update buttons, status messages, and main landmark. On phones, profile creation and renaming sit under an `Opcje profilu` disclosure and the profile label shows compact storage/connection status, keeping the primary task visible above the bottom navigation. `src/app/AppNavigation.tsx` renders the desktop navigation and a five-item mobile bar with an accessible More dialog. `src/app/ProfileDialog.tsx` handles profile creation and renaming; `src/app/useConfirmation.tsx` provides an in-app modal for destructive actions and unsaved-change navigation. `src/app/errorMessages.tsx` translates known technical Supabase and auth errors and leaves the original detail expandable for diagnosis. `src/app/useProfileData.ts` owns profile-scoped load state, selection, timeout, and stale-request protection; `src/app/profileRepository.ts` reads sessions, logs, and templates in parallel. `src/app/repository.ts` defines the shared interface implemented by local Dexie and cloud adapters without an unsafe cast.
- **Extracted views and actions:** `src/views/TodayView.tsx` renders the task-focused dashboard; `src/views/DiaryView.tsx` renders the pain form; `src/views/WorkoutView.tsx` renders active workout and plan preparation and focuses the new session heading after starting a workout; `src/views/HistoryView.tsx` renders charts and workout history; `src/views/SessionEditorView.tsx` renders historical workout editing; `src/views/DataView.tsx` renders local-to-cloud transfer, backup export/import, and storage instructions. Calendar, History, and Data views are loaded on demand through `React.lazy` in `main.tsx`; the HSR timer stays mounted to preserve its state. `src/app/useWorkoutActions.ts`, `usePainLogActions.ts`, and `useBackupActions.ts` handle those view writes through the selected repository.
- **UI components:** `SessionFields.tsx` edits sets in active and historical workouts and mounts an optional per-exercise `ExerciseTimer.tsx`; `SetNumberInput.tsx` is a shared numeric input; `Plans.tsx` shows saved plans before the new-plan controls and contains the exercise picker, plan editor, and optional timer settings; `Calendar.tsx` displays days with workouts and pain logs; `PainCharts.tsx` renders three pain charts; `HsrTimer.tsx` handles the standalone timer; `AppUpdater.tsx` handles service worker updates. The updater is mounted outside the data-ready view, in the desktop sidebar and above the mobile content, so it remains available when profile loading fails.
- **`src/domain.ts` — types and domain logic.** Contains Zod schemas and types for plans, sessions, sets, pain logs, and backups; validation and creation functions; set grouping and exercise replacement; local date handling; and pain-monitor lookups. Keep rules that do not depend on React or IndexedDB here.
- **`src/catalog.ts` — exercise catalog.** Defines the initial exercise set and the full picker catalog, including equipment, laterality, and defaults. `exerciseById` is used by domain logic to resolve exercise IDs.
- **`src/db.ts` — persistence.** Defines the Dexie database `body-reconstruction-v1`, the `profiles`, `logs`, `sessions`, and `templates` tables, migrations through version 3, and transactional JSON backup import/export. Version 3 assigns existing records to the default profile. Import validates data with schemas from `domain.ts` and replaces only the selected profile's data.
- **Cloud mode:** `src/supabase.ts` creates a browser client with the public project URL and publishable key. `src/AuthGate.tsx` handles sign-in, registration, password recovery, and session changes. `src/cloudDb.ts` maps the UI model to PostgreSQL, pages large reads, and uses SQL functions for atomic writes. A set edit uses `update_session_sets`; older databases fall back to full session writes. Profile creation uses `create_profile_with_template` when installed. `supabase/bootstrap.sql` defines the new-project schema; `supabase/README.md` gives the existing/new project migration order. `20261116_relations_and_indexes.sql` adds cascading child relationships and query indexes, `20261116_canonical_rls.sql` replaces active table policies, and `20261116_safe_profile_import.sql` validates lookup references before profile replacement. Profile ownership references `auth.users` directly; `app_users` is legacy and inaccessible to browser roles.
- **Cloud timestamps:** `src/cloudDb.ts` converts PostgreSQL `timestamptz` values to UTC ISO strings before passing sessions and pain logs to the domain schemas. The domain schemas expect timestamps ending in `Z`; see `src/cloudDb.test.ts` for offset regression coverage.
- **Timer:** `src/intervalTimer.ts` contains pure settings, validation, position calculation, and formatting logic; `HsrTimer.tsx` implements the standalone UI and `ExerciseTimer.tsx` uses a saved session exercise configuration. The final `min(5, rest)` seconds of each between-set rest are shown as preparation for the next set and remain part of the rest duration. Standalone timer settings use `timer_settings` in cloud mode and per-profile `localStorage`; per-exercise timer configuration is included in templates, session snapshots, and backups.
- **Styles and assets:** `src/style.css` imports ordered modules from `src/styles/` and applies the final phone layout overrides; `tokens.css` defines shared colors. `public/` contains icons, the source manifest, and static files. `index.html` is the app entry document.

## Data Flow

1. On startup, `src/main.tsx` selects Supabase when both public environment variables are present. Authenticated users load profiles and their records through `src/cloudDb.ts`; otherwise the app uses `src/db.ts` (Dexie). Switching profiles clears view state before loading the next person's records.
2. User interactions pass through focused action hooks and view/form handlers in `main.tsx` and specialized components. Rules and validation live in `src/domain.ts` (Zod); exercise data comes from `src/catalog.ts`.
3. Local mode writes to IndexedDB. Cloud mode uses profile-scoped Supabase tables and RPCs. Most writes refresh the selected profile, while edits to existing set rows update only those rows and then update local React state. Each workout session stores its own copy of the plan, so later template edits do not change workout history.
4. Export creates a v3 JSON file containing the selected profile's name, pain logs, sessions, and templates. Import accepts v1, v2, and v3 and replaces only the selected profile's data. Cloud import runs in one PostgreSQL function call. The Data tab can transfer an existing local profile into the signed-in account without deleting the local copy.
5. In production, `src/main.tsx` registers the service worker generated by `vite.config.ts`. The Vite configuration builds the manifest and offline cache using `VITE_BASE_PATH` (including for GitHub Pages). The service worker ignores query parameters for navigation cache matches, so `?view=` deep links reload offline.

## Tests and Tooling

- Vitest unit tests live alongside the code in `src/*.test.ts`. They cover domain rules, validation and editing (`domain.test.ts`, `editing.test.ts`), the database and backups (`db.test.ts`), plans (`plans.test.ts`), and timer calculations (`intervalTimer.test.ts`). Vitest includes `src/**/*.test.ts`.
- Playwright end-to-end tests are in `e2e/`; phone emulation, the `Europe/Warsaw` timezone, and the preview server are configured in `playwright.config.ts`. Scenarios cover the app, history, pain tracking, plans, workouts/sets, profile isolation, the timer, and updates/offline behavior. `e2e/responsive-navigation.spec.ts` checks navigation and overflow at 320, 390, 768, 1024, and 1440px; `e2e/profiles.spec.ts` checks that switching profiles does not expose another profile's pain entry.
- `TESTOWANIE.md` documents test coverage and environment notes; `README.md` describes setup, Pages hosting, features, and privacy.
- Commands from `package.json`: `npm run dev` starts Vite, `npm run build` runs the TypeScript check and builds `dist`, `npm run preview` serves the build, and `npm test` runs Vitest. For E2E tests, build the app first, then run `npx playwright test`.

## Deployment Configuration

- `vite.config.ts` reads the base path from `VITE_BASE_PATH`, validates its format, and generates the manifest and service worker in `dist`. Builds for a subpath should use the same path as the Playwright configuration.
- `vitest.config.ts` limits unit tests to `src/**/*.test.ts`; `playwright.config.ts` points to `e2e/` and starts `npm run preview` on port 4176.
- `START.ps1` is a local startup script. `public/manifest.webmanifest` is a static manifest asset; the production manifest is generated for the build by the Vite configuration. `supabase/migrations/20261116_schema_audit.sql` reports live schema metadata and duplicate/orphan counts before applying integrity changes.
