# Architecture Map

Cloud read optimization: `src/app/resourceCache.ts` holds account-lifetime, profile-keyed resources, deduplicates pending reads, clones snapshots, expires records at 30 seconds (profile/templates 120 seconds), and rejects/cancels invalidated in-flight loads. `src/supabase.ts` clears cache on auth owner changes; `apiTransport.ts` bounds requests to six per client and enforces abortable queue/request deadlines without adding a mutation retry loop. Confirmed cloud mutations patch or invalidate the affected cache; imports clear all affected resources. Export bypasses cache. `useProfileData.ts` uses `cloudDb.readRecent` for startup, then gates History/Calendar/Analytics behind complete history loading. Local Dexie remains unchanged. `20261123_read_record_pages.sql` adds invoker/RLS-protected GET RPC keyset pages containing child records, with a compatible legacy-read fallback only for a missing RPC. Recent mode includes active and latest performed workout, plus linked measurements. It is not yet server-filtered per analytics/calendar period; complete history is still required there. Version-conflict handling and mutation idempotency ledgers remain future work, not claimed implemented.

Load/performance checks: `npm run test:load` uses `vitest.performance.config.ts` and `src/performance/cloud-load.perf.ts`, excluded from ordinary tests. It exercises the real cloud adapter/Supabase HTTP client against a loopback synthetic API with 5–125 actors, pagination, repeated reads, targeted writes and 503s. It never targets a real project and does not validate PostgreSQL/RLS or write durability. Findings, retained measurements, staging acceptance steps and read-only database diagnostics are in `docs/performance/`.

`src/analytics/PeriodExplorer.tsx` adds 7/30/90-day shortcuts, daily workout-count bars and selected-day hourly reports to Analytics. It consumes the existing filtered range and updates the shared URL date filters; no database changes or additional requests. Daily bars count sessions with performed work and the hourly list preserves separate reports.

Language persistence: `accountRepository.ts` owns the per-profile write queue and pending cache confirmation; writes survive navigation away from Preferences. `LanguageSettings.tsx` observes in-flight writes and reconciles stale pending markers against the loaded profile preference. A missing language RPC falls back to updating only `profiles.preferred_language` through existing owner RLS, verifying the returned row. Permission failures remain errors; the frontend never bypasses RLS.

Project documentation lives under `docs/`; the root `README.md` is the entry point. File paths in this map and command examples in project documentation are relative to the repository root, unless stated otherwise. Local skill packages live in `docs/skills/` and remain excluded from version control; their internal directory structure and supporting assets are preserved.

Body Reconstruction is a React + TypeScript single-page app built with Vite. Supabase is the authenticated cloud persistence layer; Dexie IndexedDB remains available for local use and migration. Read this file before code changes and keep it aligned with the implementation. Follow `docs/AGENTS.md` and relevant instructions in `docs/skills/*/SKILL.md`; use `docs/CODE_PRACTICES.md`.

## Data Ownership and Flow

- Every authenticated Supabase user owns exactly one `public.profiles` row. The profile ID is resolved from the database at startup; there is no account-profile picker or add/rename dialog. Profile configuration is changed in the Settings view and persisted atomically through `save_profile_settings_with_archiving`.
- The profile stores its display name, weekly workout target, default diary check-in time, ordered monitored rehabilitation areas, and diary context choices. `profile_rehab_sites` and `profile_pain_contexts` are profile-owned rows protected by RLS. Deactivating an area hides it from future diary forms; archiving removes it from settings and new forms while preserving its identity, injury links, and historic pain values. Dexie v6 defaults old areas to unarchived; Supabase migration `20261118_rehab_site_archiving.sql` adds the cloud column and atomic settings RPC.
- Diary `PainLog.values` is a list of `{ siteId, value }`, so user-defined tracked areas work throughout the form, history, calendar, workout comparison, charts, and backup. The domain schema and Dexie migration accept the former fixed three-number format and convert it to the standard IDs. Backups are version 6; versions 1–5 remain readable. Import remaps session IDs before restoring diary relationships; dangling references are detached without removing measurements.
- Profile settings contain injury episodes with status, dates, side, notes, and links to monitored areas. Diary logs can reference multiple injuries through `injuryIds`; Supabase stores these links in `pain_log_injuries` while local Dexie and backup v6 keep the same app-level shape. Earlier backups remain importable with no injury associations.
- Progress summaries use the profile's already loaded records without extra render-time requests. `src/analytics.ts` compares equal calendar periods using means of daily medians. `src/analytics/metrics.ts` owns daily aggregation, weekly dose and validation/remapping of report links. `matching.ts` distinguishes confirmed links from time candidates, checks context, elapsed windows (18–30/42–54 h after session end), and intervening actual sessions. These are descriptive product rules, not medical thresholds or causal inference.
- `AnalyticsView.tsx` composes Overview, Timeline, Session response, Dose/regularity, and Areas/injuries. `useAnalyticsNavigation.ts` stores shared filters and session selection in the URL and handles browser history. Area/injury/context/phase session filters require explicit log links; plan/exercise report filters also require links. Response matching can access loaded logs outside the selected session range. Dose comparisons require confirmed, same-context baseline/follow-up pairs without intervening training. Reports, timeline rows and dose rows initially show 50 items. Charts use the entire range in Analytics (daily medians by default, raw points optional); History retains the last-14 default. Gaps are not interpolated. Analytics and charts load lazily.
- Diary creates independent reports rather than replacing the latest entry on a date. History/Analytics edit an exact ID; choosing a date or New measurement starts a separate entry. `measurementPhase` (daily/pre/during/post/followup/unspecified) is independent of context. Optional `sessionId` belongs to the same profile. Existing entries retain their original areas and archived context when edited. Post-workout reports receive a fresh UUID and explicit session/post metadata. Optional `completionReason` records the user's reason for early completion; it is not inferred from pain.
- Dexie v7 indexes session links and measurement times without inferring old relationships. The local repository validates link ownership/timing on report and session writes; session deletion detaches reports transactionally. Supabase migration `20261121_analytics_links.sql` adds metadata, a composite ownership FK, indexes, validation/deletion triggers and atomic save/import wrappers. The application requires these new RPCs for cloud writes and gives an actionable missing-migration error. Existing RLS remains in effect. Today counts sessions with actual performed work and shows seven-day performed sets, diary coverage and last-session post-report status.
- Cloud reads and writes flow through `src/cloudDb.ts`; untrusted imports and writes are validated in `src/domain.ts`. SQL functions perform atomic writes. Browser code uses only the Supabase URL and publishable key; row-level security enforces account ownership. Never put a secret key in the frontend.
- A workout can end with fewer completed sets than planned. Unfinished exercise IDs receive `finishedEarly` in `exerciseProgress`, while their unfinished set rows keep `done=false`; the status and `ended` timestamp are saved in one session write. History displays completed versus planned set groups and distinguishes early completion.
- Both the Today active-workout card and Workout view call the same `finishWorkout` action. Today allows ending without opening the set editor; incomplete workouts require the shared completed/planned confirmation.
- Workout also exposes an early-finish action above the exercise list, preserving selected post-workout pain values and using the same completion validation and confirmation as the bottom action.
- Diary and workout completion use a shared 0–10 pain slider. When opted in, workout completion saves a separate diary log at the completion time for every active rehabilitation area; that log is then included in history and analytics. The session is saved first, so a diary write failure leaves the completed session intact and shows a message to add the measurement in Diary.
- The account consolidation migration moves all prior profile-owned workouts, templates, logs, and timer settings under one canonical account profile before adding unique ownership. It preserves multiple diary rows on the same date and leaves old global `pain_sites` lookup rows unused for compatibility.
- Local Dexie remains multi-profile only to support old local data and source selection during local-to-cloud migration. The normal app shell no longer offers profile switching.

## UI and Responsive Structure

Today dashboard: `src/today/TodayDashboard.tsx` replaces the generic plan hero with seven-day workout/diary progress rings, completed-set bars, time since the last completed workout and per-area pain mini charts. `dashboardData.ts` reuses `sessionDose` and `dailyMeasurements`: only actual ended workouts count, diary coverage counts distinct days, chart points are daily medians, missing dates remain gaps and zero is a real measurement. Area cards show the latest raw rating within the range separately from the median chart; archived/inactive areas are excluded. No health/readiness score is inferred. `TodayView.tsx` keeps active-workout completion/resume and diary actions; `src/styles/dashboard.css` owns responsive dashboard geometry. Tests: `src/today/dashboardData.test.ts`, `e2e/today-dashboard.spec.ts`.

Calendar: `src/Calendar.tsx` owns month/day selection and keyboard/focus navigation. Desktop selection opens a narrower month on the left and `src/calendar/CalendarDayDetails.tsx` on the right; smaller screens stack details below. `calendarData.ts` groups already-loaded sessions by the existing start-day convention and reports by their recorded date, retaining every report and sorting by measurement instant. `CalendarWorkoutCard.tsx` uses existing bilateral/unilateral set-group counting; `CalendarPainCard.tsx` displays individual values, phase, context, injury links and notes. Calendar edits target report IDs; Add measurement always starts a fresh diary entry. No schema change or extra network reads. Tests: `src/calendar/calendarData.test.ts`, `e2e/calendar-details.spec.ts`.

Successful diary writes reset to a new measurement on the selected day: ratings, note, context, injury/session links and edit identity are cleared; time returns to the profile default and phase to daily. Failed writes preserve the draft. `src/app/useNotice.ts` assigns a fresh identity to each global notice (including repeated identical messages). `ToastNotice.tsx` renders it in a persistent polite live region, without focus/click handlers or pointer interception. `src/styles/toast.css` places it above mobile navigation, fades after four seconds and removes it at 4.4 seconds, with reduced-motion support. Errors remain persistent and separate from these transient confirmations.

`LoadingScreen.tsx` provides full-screen startup, content-area lazy-view and small inline background-refresh variants. Startup uses the page color, a CSS ring and “Wczytywanie…”; reduced motion disables rotation. `AuthGate` delegates initial session resolution and auth subscription cleanup to `watchAuthSession.ts`, which bounds startup at 15 seconds, ignores stale initial results after auth events/unmount/timeout, and permits a fresh retry after failure. Password recovery events remain authoritative. `main.tsx` uses the same full-screen presentation until first profile records resolve; later background refreshes keep the shell, forms and timer mounted, with an inline status and aria-busy. Failed profile reads retain existing error/retry and account access.

More navigation uses `.nav-icon` for ordinary symbols, so icon width selectors no longer resize the shared avatar. More avatars are 32px square and overview/form avatars retain their existing square sizes and cropped photos. Date/time/datetime-local controls have explicit border-box inline bounds; `.date-time-fields` stacks Diary and historical-session date groups on mobile. Native pickers, seconds and parsing remain intact. Geometry and loading regressions are in `e2e/mobile-controls.spec.ts`; physical-device Safari verification remains separate from Chromium emulation.

Layout rules use horizontal checkbox/toggle labels independently of ordinary stacked form labels. Rehabilitation sections own their spacing, without accumulated paragraph/label margins; narrow screens stack form columns and section actions. Desktop shell uses the viewport width, bounded left-aligned forms and top-aligned sidebar rows (no vertical grid stretching). `e2e/rehab-layout.spec.ts` checks geometry, unclipped buttons and overflow from 320 to 1920px.

Timers optionally run a full repetition block on the first side, a separate configurable side-change preparation, and a full block on the second side before resting. A set always covers both sides; first side is configurable. Existing timers without the optional fields remain bilateral. New exercise timers default to the catalog exercise's unilateral flag. Per-exercise options remain in timer_config JSONB/session snapshots and backups; standalone settings use local storage or new timer_settings columns. Cloud reads do not replace running/dirty settings and writes are serialized. Preparation at the end of a rest retains the previous five-second behavior.

Desktop account access is a header disclosure (`AccountMenu.tsx`). Mobile navigation is Today, Workout, Plans, Diary and More; Profile is in More, whose active state also covers profile sections. `AccountProfileView.tsx` renders identity, security, preferences and application settings. Rehabilitation and Data reuse existing views with shared section navigation. Canonical URLs use `?view=profile&section=...`; old settings/data URLs remain readable. Mobile refresh lives in the Application section; desktop retains its sidebar updater. `src/styles/desktop.css` owns desktop density and the two-column Today action layout; Today greets the loaded profile by name, with a neutral fallback.

Auth User is passed separately from the database Profile. `accountRepository.ts` saves name/time zone/avatar through the focused `update_account_identity` RPC, without resubmitting rehabilitation arrays. Cloud profile reads tolerate missing avatar values before migration. Avatars use private Storage paths; signed URLs are transient and images fall back to initials. Local identity uses Dexie partial updates; no authentication fields or avatar files enter backup v6. Date conventions for existing diary/history forms remain unchanged.

Account deletion calls a deployed Edge Function which validates bearer identity and current password, removes avatar objects, calls the service-role-only transactional database cleanup, then deletes the Auth user. This is not a distributed transaction. MFA-enabled deletion is refused pending an MFA-aware flow. Browser code contains no administrative secret. Deployment and manual security verification are documented in `docs/supabase/README.md`.

UI refinement scope and acceptance results are tracked in `docs/UI_REFINEMENT_PLAN.md`. `TodayView.tsx` prioritizes workout progress and diary actions; `PainSlider.tsx` owns the shared labeled, initially unrated pain control. Responsive navigation and updater placement checks live in `e2e/responsive-navigation.spec.ts` and `e2e/update.spec.ts`.

`src/app/AppShell.tsx` owns the sidebar, account sign-out, update controls, status and app landmarks. `src/app/AppNavigation.tsx` renders desktop navigation and the mobile More dialog. `src/main.tsx` composes the screen views and action hooks. `ProfileSettingsView.tsx` edits account configuration, tracked areas, and injury episodes; `DiaryView.tsx` renders configured areas, contexts, and injury selectors. `AnalyticsView.tsx` filters and summarizes health/workout records. `TodayView.tsx`, `HistoryView.tsx`, `Calendar.tsx`, `PainCharts.tsx`, and `WorkoutView.tsx` consume the same profile-defined tracked areas. Shared responsive tokens and breakpoints live in `src/styles/`.

## Supabase Setup

The explicit refresh action in `src/AppUpdater.tsx` activates the waiting worker and clears only caches with this app's `rehab-<base>-` prefix before reloading. IndexedDB and authentication storage are preserved. `vite.config.ts` generates the production service worker and manifest, including the light theme colors.

`public/icon.svg` is the single artwork source: a coral rounded tile and dark diagonal arrow on the light page colour, matching the app brand. `npm run generate:icons` exports the committed 32px favicon, 180px Apple icon and 192/512px PWA PNGs using the locally installed Playwright Chromium (no external resources). Manifest icons support both any and maskable purposes. `vite.config.ts` owns one manifest definition for the dev middleware and production output; there is no duplicate static public manifest. The worker precaches favicon/PWA assets with reload requests. `public/connection.txt` is an English static-file diagnostic and explicitly does not test Auth or Supabase.

`npm run verify:pages -- /body-reconstruction-20/` checks generated HTML references, lazy JS/CSS imports, PNG dimensions, manifest base/scope/id, precached files and accidental source/environment/privileged-key inclusion. The workflow runs its regression tests and verifies both `dist` and the copied publication directory before committing. Only generated assets belong to `gh-pages`; do not merge source branches into it. See `docs/PAGES_ASSETS.md` for the prepared local worktree and publication rules.

For an existing project, apply the migration sequence in `docs/supabase/README.md`, ending with `20261121_analytics_links.sql`. Migrations are applied manually in Supabase SQL Editor; GitHub Pages deployment does not modify the database. New projects use `supabase/bootstrap.sql` and then the documented migrations.

Unit tests are colocated in `src/*.test.ts`; end-to-end scenarios are under `e2e/`. `npm run build` performs TypeScript checking and creates the Vite build; `npm test` runs Vitest. Do not claim checks passed unless they were run.
